Detached Ed25519 seals for WACZ web archives

waxseal builds a deterministic Merkle root over every member of a WACZ web archive and signs that root with Ed25519. It writes a detached seal.json that verifies offline against node:crypto, and it emits an inclusion proof for any single file. The project is MIT licensed and written in TypeScript for Bun; verification uses only local node:crypto calls. 

# One-line install (installs the `waxseal` binary)
curl -fsSL https://raw.githubusercontent.com/srivtx/waxseal/main/install.sh | sh

# Or run once, without installing
bunx github:srivtx/waxseal seal archive.wacz

# Install globally
bun add -g github:srivtx/waxseal
waxseal seal archive.wacz

# Add to a project as a dev dependency
bun add -d github:srivtx/waxseal

waxseal is not published to npm. Install it with the one-line script, or run it without installing.

What the current WACZ tooling does not provide

A WACZ already carries per-resource hashes in datapackage.json and datapackage-digest.json. What the ecosystem lacks is a detached, portable proof, and the existing tools each stop short of one.

Validates the in-archive chain

py-wacz checks that datapackage-digest.json matches datapackage.json and every resource hash and byte count. It is Python, and its check is bound to the ZIP it validates.

source

Reads and replays WACZ

wabac.js is a JavaScript WACZ loader for replay tooling. It understands the archive format and provides no signing layer and no Merkle commitments.

source

Replay in the browser

ReplayWeb.page serves and replays WACZ archives client-side. It is a reading and replay tool, not an integrity or provenance tool.

source

Structural checks only

waczerciser exercises ZIP structure and datapackage shape to catch malformed archives. It performs no cryptography and emits no signature.

source
  • A detached proof. The WACZ signature lives inside the ZIP it attests to, so it cannot be pinned, notarized, or distributed out of band. waxseal emits a separate seal.json.
  • A Merkle root. Everything else is a flat, one-level hash chain, so there are no inclusion or consistency proofs.
  • Ed25519. The spec and implementations use anonymous ECDSA or X.509 ECDSA.
  • A TypeScript implementation. py-wacz is Python; wabac.js and ReplayWeb.page are read/replay-only; waczerciser has no crypto.

One deterministic root over every member

The Merkle root is independent of how the ZIP was produced, so re-zipping the same logical content yields the same root. Each stage below is fixed and reproducible.

  1. 1
    Digest every member. Every file in the archive becomes a (normalized path, content SHA-256) pair.
  2. 2
    Sort and domain-separate. Sort by normalized path, then hash each leaf with an explicit domain prefix so leaves and nodes can never be confused.
  3. 3
    Promote and combine. Pair nodes level by level; the last node of an odd level is carried up unchanged, never duplicated.
  4. 4
    Sign the root. Ed25519 signs a canonical JSON payload — the signature covers the root, member count, algorithm, and the archive's byte hash.
  5. 5
    Verify offline. Rebuild the root from the archive, check the signature, and check any inclusion proof — no network, no server.
Member-level vs byte-level

Membership is a set of (normalized path, content SHA-256) pairs, so a member-level check tolerates a legitimate re-zip. archiveSha256 pins the exact bytes instead: verifySeal(seal, data, { strictBytes: true }) fails if the archive differs in any way — including appended trailing bytes that leave every member unchanged.

The CLI defaults to strict byte-level verification; --member-only relaxes it for reproducible re-packaging. The library default is member-level.

Command-line interface

Signing and verification run locally against node:crypto. Run waxseal --help for the full list, or waxseal --version for the installed version.

Commands and options. Copy runs a concrete example; the table shows the usage form.
Command What it does
waxseal keygen [--out <base>] Generate an Ed25519 key pair (default base: waxseal-key) → archive-key.pem (private), archive-key.pub.pem (public).
waxseal seal <archive.wacz> [--key <pem>] [--out <seal.json>] [--proofs <proofs.json>] [--json] Create a detached seal for an archive.
waxseal verify <archive.wacz> -s <seal.json> [--json] [--member-only] Verify an archive against a seal. Default: strict byte-level check; --member-only allows a re-zip.
waxseal proof-verify <archive.wacz> --proofs <proofs.json> [--path <member>] [--json] Verify Merkle inclusion proofs against the archive's rebuilt root (default: every proof in the file).
waxseal inspect <archive.wacz> [--json] Inspect members, datapackage digest status, and root. 
# 1. create a key pair
waxseal keygen --out archive-key

# 2. seal once, emit a seal and one proof per member
waxseal seal capture.wacz --key archive-key.pem --out capture.seal.json

# 3. verify later, fully offline
waxseal verify capture.wacz -s capture.seal.json

A passing check shows that the archive contains exactly the members the signer committed to — no additions, removals, or modifications — that the signer held the private key for the embedded public key, and, with strictBytes, that the file is byte-for-byte the one that was sealed. It does not prove identity and provides no trusted timestamp: createdAt is self-asserted by the signer.

              Frequently asked questions
            

          


          

            

              Is anything uploaded when I use the demo?
              

                

                  No. The bundled SHA-256 and Merkle code run entirely in this
                  tab, and the page makes no network requests. Reload the page
                  and the state is gone.
                

              

            


            

              Does a valid seal prove who signed it?
              

                

                  No. It proves the signer held the private key matching the
                  embedded public key, and that the archive matches the committed
                  root. There is no identity or trust model for that key.
                

              

            


            

              Does it prove when the archive was sealed?
              

                

                  No trusted timestamp. createdAt is
                  self-asserted by the signer. Pair the root with a timestamping
                  authority if you need a proven "existed before" time.
                

              

            


            

              What happens if I re-zip the same content?
              

                

                  A member-level check tolerates it, because leaves are
                  (normalized path, content SHA-256)
                  pairs and the root is unchanged. Strict byte mode
                  (archiveSha256) catches any byte
                  difference, including appended trailing bytes that leave every
                  member unchanged.
                

              

            


            

              How does waxseal relate to py-wacz?
              

                

                  They are complementary. py-wacz validates the WACZ's own
                  datapackage chain inside the archive; waxseal adds a detached,
                  portable Merkle-and-Ed25519 proof layer on top of the same
                  members.
                

              

            


            

              Why can't the browser demo sign?
              

                

                  Ed25519 key generation, signing, and signature verification
                  require the CLI. The demo intentionally covers only the Merkle
                  root and inclusion proofs, which run fully client-side.
